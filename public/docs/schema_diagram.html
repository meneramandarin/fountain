polymorphic relationships — how entity_type + entity_id works

Three tables — entity_tags, images, and source_records — use a polymorphic pattern instead of separate per-entity FK columns. Each row carries an entity_type TEXT discriminator and an entity_id INT that points to the matching table's PK.


This means no foreign key constraint is enforced by SQLite on entity_id — integrity is maintained at application level. New entity types can be added without schema migrations.

edge cases & design notes

Null-tolerant pricing — offerings.price_amount and price_currency are both nullable. Only 917 of 16,064 rows (6%) have a numeric price. locations.price_text captures free-form strings like "from $3,500/day" when structured pricing isn't available.


Dual price fields — a location has price_text (free-form, source-level) while each offering has price_amount + price_currency (structured, per-treatment). These are independent; a location can have price_text with no offering prices, or vice versa.


Review rating as TEXT — reviews.rating is TEXT, not REAL, to capture raw scraped values ("4.5/5", "★★★★☆"). The aggregate locations.rating is REAL for filtering. Both fields can coexist for the same location.

Offerings with unmapped treatments — when a scraper finds a treatment string that doesn't match any alias, offerings.treatment_id is set to NULL and the raw string goes into unmapped_terms. The offering row is still created so no data is lost.


Dedup strategy — organizations dedup on website_domain first, falling back to name_normalized + country. Locations have their own dedup_key (schema-defined, build-populated). Multiple source listings can map to one canonical entity via source_records.


Fully disposable DB — canonical.db has no hand-edited data. It is rebuilt from staging DBs on every scrape run. The only durable curation artifact is treatment_aliases (and treatments / categories), which are seeded from data_pipeline/taxonomy_seed.json.
